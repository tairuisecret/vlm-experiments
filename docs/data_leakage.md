## 二、数据泄漏事件完整复盘（重点学习材料）

### 2.1 事情是怎么暴露的

第一轮实验结果看起来非常漂亮：

| 指标 | 数值 |
|---|---|
| 训练 loss | 1.41 → **0.0013** |
| token 准确率 | 0.889 → **0.999** |
| 验证集精确匹配 | 47.0% → **86.4%** |

**可疑点**：训练 loss 降到 0.0013 意味着模型几乎完美拟合了训练集。对于一个只训练了 0.5% 参数、只跑了 1 个 epoch 的 LoRA 来说，这不正常。

真正触发排查的是另一件事：准备把验证集从 66 条扩大到 500 条时，需要确认"哪些数据没被训练过"，于是去查了数据集的实际构成。

### 2.2 根因分析

```bash
# 查数据集真实规模
AI-ModelScope/LaTeX_OCR:human_handwrite
  总行数：1,338
  唯一公式：295        ← 关键
```

而训练命令里写的是：

```bash
--dataset "AI-ModelScope/LaTeX_OCR:human_handwrite#20000"
```

`#20000` 的语义是"采样 2 万条"。**当数据集不足 2 万条时，ms-swift 会重复采样来凑数**——1,338 行被重复约 15 倍，得到 19,934 行。

致命的是顺序：

```
原始数据 1,338 行
   ↓ 重复采样 15 倍
19,934 行（每条出现约 15 次）
   ↓ 按 5% 随机切分          ← 切分发生在重复之后
训练集 19,934 行 / 验证集 66 行
```

因为每条数据都有约 15 个副本，随机切分时**副本必然同时落入训练集和验证集**。

实测验证：

```
train 去重后唯一公式：295
val   去重后唯一公式：23
验证集与训练集重叠：23 条（100.0%）
```

**验证集里的每一条，模型在训练时都见过。**

### 2.3 影响评估

| 受影响的结论 | 是否可用 | 说明 |
|---|---|---|
| 精确匹配 47% → 86.4% | ❌ 作废 | 在模型背过的数据上测的 |
| 字符相似度 89.6% → 97.4% | ❌ 作废 | 同上 |
| "2 万条训练样本" | ❌ 不准确 | 实际只有 295 条唯一公式 |
| 过拟合 / 早停结论 | ⚠️ 需重验 | 现象是真的，但根因是数据重复而非正常的容量过剩 |
| 显存 33.8GB、耗时 68 分钟 | ✅ 有效 | 与数据内容无关 |
| 可训练参数 43.6M / 0.5% | ✅ 有效 | 由模型结构决定 |
| 基线模型 47% 这个数字本身 | ⚠️ 半有效 | 基线没训练过，不存在泄漏，但样本量仅 66 条 |

### 2.4 修复方案

换用同一数据集的大子集，并**按公式去重后再切分**：

```
AI-ModelScope/LaTeX_OCR:synthetic_handwrite
  总行数：95,424
  唯一公式：94,655      ← 几乎无重复
```

修复后的切分流程（`prep_clean.py`）：

```python
seen = set(); rows = []
for i, r in enumerate(d):
    t = r["text"].strip()
    if t in seen: continue      # ① 先按公式文本去重
    seen.add(t); rows.append((i, r["image"], t))
    if len(rows) >= 20500: break
random.shuffle(rows)             # ② 再打乱
val, train = rows[:500], rows[500:]   # ③ 最后切分
```

验证结果：

```
train 20000  val 500  公式重叠 0   ✅
```

**关键顺序：先去重 → 再打乱 → 最后切分。** 任何一步颠倒都可能引入泄漏。

## 三、从这件事该学到什么

### 3.1 数据泄漏（Data Leakage）是什么

**定义**：评测数据以任何形式出现在训练数据中，导致评测指标虚高，无法反映模型的真实泛化能力。

**常见形式**：

| 类型 | 例子 |
|---|---|
| 直接泄漏 | 验证集样本原样出现在训练集（**本次就是这种**） |
| 重复样本泄漏 | 数据集内部有重复条目，随机切分后分散到两边 |
| 近似泄漏 | 同一张图的不同裁剪/增强版本分别在训练和验证集 |
| 时间泄漏 | 时序数据用未来信息预测过去 |
| 特征泄漏 | 特征中混入了与标签直接相关的信息（如 ID 编号隐含类别） |

**为什么危害极大**：一个泄漏的 benchmark 会让整个团队朝错误方向优化数月。指标涨了，线上效果不动，还找不到原因。

### 3.2 识别泄漏的信号

以下现象出现时，**先怀疑评测而不是庆祝**：

- 训练 loss 异常低（接近 0）
- 验证指标好得不符合任务难度
- 验证 loss 与训练 loss 同步下降且差距极小
- 小模型/少量参数就达到了很高的指标
- 换一批数据测试，指标大幅下降

### 3.3 防御清单（可直接用于以后的项目）

```
□ 切分前先检查数据集的唯一样本数（不只是行数）
□ 去重在切分之前完成
□ 切分后验证：train 与 val 的关键字段零重叠
□ 使用框架的采样参数（如 #N）时，确认数据量是否足够，是否会触发重复采样
□ 图像类任务：除了标签，还要检查图像本身（哈希）是否重复
□ 记录随机种子，保证切分可复现
□ 最终评测使用完全独立的 test set，而不是调参时用的 val set
```

### 3.4 这件事在面试中怎么讲

这是**最有价值的面试素材**，因为它展示的是"质疑自己结果"的能力，而不是"会跑脚本"的能力。

> "我第一版实验拿到了 86% 的精确匹配，但训练 loss 降到了 0.001，这对一个只训 0.5% 参数的 LoRA 来说不正常。我去查数据来源，发现这个子集只有 295 条唯一公式，而我指定的 2 万样本量触发了框架的重复采样，重复又发生在切验证集之前，导致验证集 100% 泄漏。
>
> 我换成了 9.5 万条的子集，按公式文本去重后重新切分，确认零重叠再重测。这件事之后我形成一个习惯：**拿到好看的数字，先怀疑评测本身。**"

**加分点**：如果能同时给出"泄漏数据上 86.4%"和"干净数据上 XX%"两个数字，就量化了评测不严谨会虚报多少，说服力极强。

## 四、rank 消融实验设计

### 4.1 实验目的

回答面试必问题：**"LoRA 的 rank 怎么选？"**

不是背诵"一般 8-16"，而是用自己的数据说话。

### 4.2 变量控制

| 固定不变 | 唯一变量 |
|---|---|
| 模型 Qwen3-VL-8B、数据（train 20000 / val 500）、lr 1e-4、warmup 5%、有效 batch 32、1 epoch、冻结 ViT、bf16 + 双卡 DDP | **lora_rank = 8 / 16 / 32**（alpha 同步取 2×rank） |

**注意 alpha 跟着 rank 走**：LoRA 的缩放系数是 `α/r`，保持 `α = 2r` 意味着缩放系数恒为 2，这样比较的才是"秩的大小"本身，而不是"缩放强度"的混合效应。这是消融实验设计的基本功——**一次只变一个因素**。

### 4.3 预期观察

| rank | 可训练参数 | 占比 | 预期 |
|---|---|---|---|
| 8 | 21.8M | 0.25% | 容量小，可能欠拟合 |
| 16 | 43.6M | 0.50% | 基准 |
| 32 | 87.3M | 1.00% | 容量大，可能过拟合、显存更高 |

**要看的不只是最终指标**，还有：
- 各 rank 的 eval loss 曲线拐点位置（过拟合早晚）
- 显存占用差异
- 收益是否随 rank 线性增长（大概率不是，会饱和）

### 4.4 结论写法

跑完后应该能写出这样一句：

> "在 2 万条样本的垂域任务上，rank 从 8 提升到 16 带来 X 个点的提升，但从 16 到 32 只有 Y 个点，而显存增加 Z GB —— 说明该任务的权重更新量的有效秩在 16 附近饱和，继续增大 rank 只增加过拟合风险。"
